# Add website report collection for reviews and articles CSV exports

## Plan

Collect the Review Report (`reviews-*.csv`) directly from the OJS website, so the
reviews ingestion path no longer depends on a manual dashboard CSV export. Today
`ojs reviews norm` consumes a hand-exported `reviews-*.csv` (matched by the fixed
`REVIEWS_GLOB` constant in `ojs/cli.py`); this would automate fetching that export. The website pipeline
under `ojs/website/reviews/` is currently normalize-only (`normalize.py` +
`schemas.py`, no fetch step), so this adds the collection front-end to it.

The Articles Report (`articles-*.csv`) is produced by the **same** OJS dashboard
report mechanism and feeds `ojs articles norm` the same way. Rather than build a
reviews-only fetcher and duplicate it later, this plan factors the download
machinery into one shared module and wires up both `ojs reviews fetch` and
`ojs articles fetch` on top of it.

### Background: how the report export works

The Review and Articles reports are **not** REST endpoints. They are generated by
OJS report plugins reached through the editorial dashboard (Statistics > Tools),
which stream a CSV directly from a page/tools handler. Two consequences follow
from plan [000](../000-submission-file-downloads/plan.md), which probed this
instance's auth model:

- These handlers authenticate by **session cookie**, not the REST `apiToken` the
  `api` pipeline uses. Plan 000 confirmed the token is rejected on the
  editorial-UI/grid handlers; the tools/report handlers are in the same web app,
  so the token path is a dead end here.
- Therefore the fetcher must establish an authenticated **session** by logging in
  with editorial-manager credentials, then GET the report URL on that session.

The exact report URL and login-form details are **instance- and version-specific**
(they differ across OJS installs and releases) and are deliberately kept out of
this public plan. The report URL is supplied at runtime through a config env var;
the real value is provided only at test time against the target instance.

### Design

#### New shared module: `ojs/website/reports.py`

A small, dependency-light (httpx only) module that both fetch commands call:

- `extract_csrf_token(html) -> str | None` — pull the login form's CSRF token out
  of the login page (OJS embeds it as a hidden `csrfToken` input and/or a JS
  `csrfToken` variable). Sent back on the login POST when present; harmless if the
  instance does not require it.
- `login(client, base_url, username, password) -> None` — GET the login page,
  extract the CSRF token, POST the credentials to the sign-in URL on the same
  `httpx.Client` (whose cookie jar retains the session cookie across the
  redirect). Raises `ReportAuthError` if the response indicates the login form was
  re-rendered (bad credentials) rather than a successful redirect.
- `fetch_report(client, report_url) -> bytes` — GET the report URL on the
  authenticated session and return the CSV bytes. Raises `ReportAuthError` if the
  body looks like an HTML login page instead of CSV (session not established /
  expired), so a silent HTML-in-a-`.csv` file never reaches the normalizer.
- `download_report(*, base_url, username, password, report_url, dest) -> Path` —
  orchestrator: opens one `httpx.Client`, logs in, fetches, and writes the bytes
  to `dest` atomically (temp file + `os.replace`, mirroring `api/sync.write_json`).

Login/sign-in URLs are derived from `OJS_BASE_URL` (`{base}/login` and
`{base}/login/signIn`, the standard OJS routes); only the report URL is
configurable, since that is what actually varies. The password is never logged,
and httpx status errors from these calls carry only the URL, not the POST body.

#### CLI commands

Mirror the existing `norm`/`schema` command shape under each app:

- `ojs reviews fetch` — download the Review Report to
  `OJS_DOWNLOADS_DIR/reviews-<YYYYMMDD>.csv`.
- `ojs articles fetch` — download the Articles Report to
  `OJS_DOWNLOADS_DIR/articles-<YYYYMMDD>.csv`.

The date-stamped filename lands in `OJS_DOWNLOADS_DIR` (the parent that
`reviews norm` / `articles norm` already glob with `REVIEWS_GLOB` /
`ARTICLES_GLOB`), so the existing `fetch -> norm` handoff works unchanged. A
same-day rerun overwrites that day's file (latest wins); `norm` picks the newest
match either way. Each command validates its required config up front and exits
non-zero with a clear message when something is missing (matching `api fetch`).

#### Configuration (new env vars)

| Var | Purpose |
|---|---|
| `OJS_USERNAME` | Editorial-manager username for website login |
| `OJS_PASSWORD` | Password for that account |
| `OJS_REVIEWS_REPORT_URL` | Review Report export URL (absolute, or path joined onto `OJS_BASE_URL`) |
| `OJS_ARTICLES_REPORT_URL` | Articles Report export URL (same rule) |

`ojs init` gains optional prompts for `OJS_USERNAME`/`OJS_PASSWORD` (password via
hidden prompt, like the API key) so the website path is scaffoldable; the report
URLs are documented in the README and added by hand (they are instance-specific).
All four are read the same way as the existing config (CWD `.env`, then the
user-level fallback). Absent vars only fail the website `fetch` commands, never
the API pipeline.

#### Output & privacy

Raw fetched CSVs contain reviewer and author personal data (names, emails, and
ORCIDs). They write under `OJS_DOWNLOADS_DIR` (default `data/`), which is **not**
currently gitignored — this plan adds `data/` to `.gitignore` so fetched exports
cannot be committed by accident, and notes the sensitivity in the README security
section (consistent with the existing note about the API JSON dumps).

### Implementation steps

1. Add `ojs/website/reports.py` (login + fetch + orchestrator + `ReportAuthError`).
2. Add `reviews fetch` and `articles fetch` commands and their config resolution
   in `cli.py`; add the report-URL resolver (absolute-vs-relative join).
3. Extend `ojs init` with optional username/password prompts.
4. Add `data/` to `.gitignore`.
5. Document the new env vars, the `fetch` commands, and the privacy note in the
   README.
6. Tests (mocked httpx, no live calls).

### Testing

Follow the existing suite's fake-client pattern (monkeypatch `reports.httpx.Client`
with a context-manager fake; `CliRunner` for the CLI):

- `extract_csrf_token` pulls the token from a sample login page (hidden input and
  JS-var forms), and returns `None` when absent.
- `login` posts username, password, and the extracted CSRF token to the sign-in
  URL, and reuses the session cookie on the follow-up GET.
- A re-rendered login form (bad credentials) raises `ReportAuthError`.
- `fetch_report` returns CSV bytes, but raises `ReportAuthError` when the body is
  an HTML login page.
- `download_report` writes the CSV to `dest` atomically.
- `reviews fetch` / `articles fetch` end-to-end: with the client mocked, the
  command writes `reviews-<date>.csv` / `articles-<date>.csv` into
  `OJS_DOWNLOADS_DIR`, and a subsequent `norm` consumes it.
- Missing `OJS_USERNAME`/`OJS_PASSWORD`/report-URL exits non-zero with a clear
  message.

Live verification against the target instance (real login, real report URL) is a
manual step run outside CI, since the credentials and URL are instance-specific.

### Out of scope / follow-ups

- Session-cookie reuse/caching across runs (each `fetch` logs in fresh).
- Incremental/delta report fetching (reports are full exports).
- A pasted-session-cookie auth alternative (automated login is the chosen path).
